# Dynamic Admin-managed reference audit

Date 2026-11-06. **Offline audit, no code changed.** Method: the real Express API on an **isolated synthetic database** (port 43310, name contains "e2e", DDL blocked, no migration) with a scripted Claude double and no network (`scripts/release/dynamic-reference-audit.cjs`; evidence `dynamic-reference-audit-current.json` for the working tree and `dynamic-reference-audit-rc2.json` for the frozen snapshot; **both give identical observations**). An Admin creates a brand-new program `ZZNEW` (not in any list) with its own EGAs and POs through the real `POST /courses`, a curriculum reference through `/syllabus-check/references`, a faculty member checks a syllabus under the comprehensive profile (Policy V2 on), the Admin edits a PO, and a new academic year is created and its catalog copied. Existing development data was only read.

**Answer in one line: the legacy checker consumes Admin-managed POs dynamically; Academic Policy V2 does not. Newly created programs cannot get their CLO-to-PO relationships evaluated, and the program's own EGAs and reference versions are not consumed or recorded.**

## Is the checker dynamic? Verdict B (summary)

Dynamic: PO masters and numbering from the database per academic-year program row, inheritance by the generic `program_outcome_sources` link, approved curriculum registry by program code, PO-EGA mapping gaps, curriculum and PO gates in the legacy rules. **Not dynamic: Policy V2's PO relationships (static JSON), per-program EGAs, institution versioning, PO version recording for unversioned programs, and the report's version/authorization labelling.**

## Minimum required changes (not implemented; no second checker, no parallel reference system)

Scope rule: use the **existing resolver** (`repository.mastersFor`, which already returns `masters.pos`, `masters.poReference`, `masters.outcomeSource`, `masters.referenceContext`, the program's `versions`) and the **existing versioned-reference tables** (`program_po_reference_versions` / `program_po_reference_active`) that the PO activation created. The 47 rules, the seven VPAA relationships, the four CLO classifications, scoring (79) and the gates stay as they are.

1. **Replace the static check in `academicV2Plan.referencesFor`** (the only V2 dependency on the JSON). `poUsable` should be true when `masters.pos` is non-empty and, if `masters.poReference` exists, `sameBasis(masters.pos, masters.poReference.outcomes)`; the inheritance test should use `masters.outcomeSource` instead of `'BSIT-CYBERSECURITY'`/`'BSIT'`. Decision for the owner: whether an **unversioned** (legacy) PO list may be judged by V2 at all. The conservative option keeps `NOT_CHECKED` until a version is published, which needs item 2.
2. **A publish action for a PO reference version** (code + the existing tables): an Admin "publish current POs as version N" that writes an immutable row to `program_po_reference_versions` and activates it, so `requireMutable` protects it afterwards. Today those rows are created only by the migration script from the static JSON. Without this, a new program can never have a versioned reference, so item 1 cannot be both safe and useful.
3. **Do not label with the official version.** `academicV2Plan.js:35` must use `masters.poReference?.version` / `authorization` and otherwise `null` / `unversioned`, never `official.*` (the fallback is the mislabelling seen above).
4. **Record versions in `referenceContext`** (code only): the program's `versions.pos` / `versions.egas`, and `institution.version` (already returned by `loadOutcomes`, dropped by `mastersFor`).
5. **Use the program's own EGAs where the program defines them** (`program_egas`, already loaded by `loadResolvedProgram`) as the `INST-EXACT` master for `egas`, falling back to the institution list; otherwise a program with its own EGAs cannot pass.
6. **Curriculum:** no change is required for correctness (registry by program code + year works), but the creation of a subject with a new program should tell the Admin that a curriculum reference must still be created and approved; optional: add an academic-year column.
7. **Vision/Mission/EGA history:** needs a versioned copy (a table or the existing reference pattern) only if reports must be re-verifiable against the text in force at the time; until then reports embed the judged text but not a version.

Database changes: none for items 1, 3, 4, 5; item 2 uses existing tables (they must exist in staging, i.e. the PO migration must be applied there, which is a separate authorization); item 7 adds a table.

## Distinctions

* **Existing four-program integration** (BSIT 9, BSIE 13, BSCpE 13, Cyber 9 inherited): works end to end, including V2 CLO-PO (`po-parity-rc2.json`: 0 NOT_CHECKED among the seven VPAA types, 4 CLO classifications, official 85/79). It works **because** their POs equal the static JSON.
* **Newly created program:** legacy rules and legacy AI pairs work; V2 CLO-PO does not; EGAs and report labelling fail as above.
* All results here are **offline, scripted**; nothing says anything about real Claude behaviour, staging or production.
