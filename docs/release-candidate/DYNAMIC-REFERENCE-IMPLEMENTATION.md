# Database-driven academic references: implementation report

Date 2026-11-06. **Implemented in code and tested against isolated synthetic databases. Active in no existing database: nothing was migrated, published or activated in development, staging or production.** No paid Claude call, no commit, push or deployment. No academic rule, scoring weight, the 79 threshold, submission or approval gate, CLO classification, VPAA relationship or cost optimization was changed.

## 1. Root cause of V2's static reference dependency

`server/lib/syllabuscheck/academicV2Plan.js` `referencesFor` decided whether a program's Program Outcomes were "usable" by comparing the PO list the checker had loaded with `officialProgramOutcomes.json` looked up by program code (and by a literal `BSIT-CYBERSECURITY` -> `BSIT`). A program that is not one of the four in that file had no entry, so every CLO-PO and CLO-anyPO relationship was held (`po_reference_review`, NOT_CHECKED) however correct its database rows. The same function also stamped every report with the file's version (`lcup-po-2026-10-29`) and authorization as a fallback, attributing another program's authority to a new program. The database side was already dynamic: `mastersFor` reads the program row of the syllabus's own academic year, inherited outcomes through `program_outcome_sources`, and the immutable published version through `program_po_reference_active`. Admin edits, however, either overwrote unversioned rows in place or were refused, and there was no way to publish a version.

## 3. Published-version workflow and Admin behavior

* **Draft:** `PUT /api/programs/:id/po-reference/draft {pos}` (Admin) stores one draft per program row in `program_po_reference_versions` with `status='draft'`, validated against the program's own EGAs. A draft never reaches the checker and never changes the live rows.
* **Publish:** `POST .../publish {authorization, confirm:true}` (Admin; a written authorization of 10-500 characters and explicit confirmation are required). It publishes the draft, or for a program with no published version its current live rows (the first version). In one transaction it writes an immutable row (label `CODE-YEAR-vN`, SHA-256, publisher, time, authorization, **`institutional_approval = not_recorded`**, the version it supersedes), marks the previous one `superseded` (never deleted or rewritten), makes the live rows equal to it, points the program row's active reference at it and writes an audit row. A PO still carried by a CLO tag cannot be dropped. Faculty receive 403.
* **Never an approval:** a save or a publication is not a formal VPAA approval; every version says so. Real institutional approval remains a separate, unrecorded step.
* **Academic year:** each year has its own program rows, so a version applies to one program row of one year. `copy-catalog` creates the new year's program without a published version; the Admin publishes for the new year. A syllabus keeps resolving the version of its own year.
* **Historical syllabi:** unchanged by design. A syllabus authored under an earlier version is refused re-checking (`po_reference_review_required`, HTTP 409) until its faculty review and adopt the new statements; its saved content and earlier reports stay as they were (the earlier report still names the earlier version).

## 4. EGA source-resolution findings

Three different things exist: the **institutional EGA master** (`institution_egas`, a default list), the **program-specific EGA assignments** (`program_egas`, entered by the Admin per program and copied into the subject and the syllabus), and the **PO-to-EGA crosswalk** (each PO's own `ega_nos`). The old `INST-EXACT` and V2 CLO-EGA validations used the institution list only, so a program with its own EGAs could never pass. Now the EGA master is the program's own list when defined (for the four existing programs it equals the institution list: verified in the development database, SELECT only, so nothing changes for them), vision and mission stay institutional, and the crosswalk keeps its own rule: a PO without an approved EGA mapping gives `P-03 NOT_CHECKED` and no mapping is invented. Nothing about Vision/Mission/EGA approval was changed.

## 7. Remaining requirements

* **Database activation (separate authorization, not done anywhere):** apply `npm run migrate-po-reference-publication` to development, staging and production in turn; the official PO migration must already exist wherever the existing programs are to stay versioned (it does in development). New programs then need an Admin to publish each year's PO version and approve a curriculum reference.
* **Institutional:** formal VPAA approval of any published reference (the system records `not_recorded`); approved PO-EGA crosswalks (P-03 stays NOT_CHECKED without them); the seven PO-mapping reviews and one curriculum review; Vision/Mission/EGA approval history (still one unversioned institution row, edited in place).
* **Not implemented:** an Admin screen for drafts and publication (the API is complete and tested; the existing Program Management UI was not changed because that area is being edited by another session); versioned Vision/Mission/EGA history; automatic carry-over of a published version into a copied academic year (deliberately not automatic).
* **Status by environment:** implemented in code: yes. Tested with an isolated database: yes. Active in development: **no** (development database untouched). Active in staging: no (does not exist). Active in production: no.
