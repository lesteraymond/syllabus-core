## 1. Root cause (Stage E.4 Phase 1)

In the E.4 resume (`docs/ai-eval-stage-e4-smoke-resume.json`), `rr-prog1-relevant` (Ref-relevance) was refused three times as `quotes_swapped`.
- Every answer put the reference's title ("Fundamentals of Java programming") in `sourceQuote` and a course phrase in `targetQuote`.
- The second and third sends were the same request at temperature 0, and they got the same answer.

The r5 wording pulled the model both ways:
- The D2 direction said `source = the course's title, description and weekly topics; target = one reference`.
- The same D2 test also called a reference's publisher its "source" ("the title and source evidently concern…", basis `title_and_source`). So "source" named a part of the reference as well as the course side of the pair.
- The scored base prompt's REF-plan line has the opposite orientation: `source = the title and opening text of a referenced page; target = the course title…`. On REF-plan the reference is the source. That line is scored and stays unchanged.

The run's stop was an empty list:
- `syseng#1` came back as `{"judgements":[]}` (6 completion tokens) and was refused as `not_answered` for all four relationships.
- That was the fourth invalid answer, which was the E.4 limit.

|---|---|---|

**"Source" now means only the pair side.**

**The quote checks are unchanged and strict.**

- These are still refused and never accepted: swapped quotes (`quotes_swapped`), a quote from the other side (`quote_wrong_side`), and a quote copied from another relationship (`quote_from_other_pair`).

## 3. Retry behaviour (`judgeStaged()` in `gemini.js`)

Every refusal now has a class (`errorClassOf()`):

| Class | Codes | Asked again |
|---|---|---|
| contract | `schema`, `invalid_label`, `invalid_bloom`, `missing_draft`, `draft_too_long`, `invalid_recommendation`, `recommendation_conflicts_label`, `recommendation_not_allowed`, `retag_not_applicable`, `retag_with_rewrite` | once, with a correction; the same problem again stops it |
| evidence | `quote_missing`, `quote_not_found`, `quote_wrong_side`, `quotes_swapped`, `quote_from_other_pair`, `empty_explanation`, `role_confusion` | once, with a correction; the same problem again stops it |
| coverage | `not_answered`, `empty_answer`, `duplicate_id`, `unknown_id` | once, with a correction; the same problem again stops it |
| output | `invalid_json`, `invalid_answer`, `incomplete_output` | in halves; the same unreadable reply to a relationship asked alone stops it |
| transient | timeout, rate limit, provider or network error | never by `judgeStaged`. A check reports a timed-out or failed batch as not checked, and stops on a rate limit or the third failure; an evaluation's guard stops at the third |
| access | HTTP 401/402/403, a refused request | never; the guard stops at once |

**A retry is always corrective.** It carries `corrections` in the request, one for each relationship asked again:
- its id;
- the codes it was refused for (`refused`);
- one fixed instruction per problem (`instruction`). For Ref-relevance the instruction names the course context and the bibliographic entry;
- the refused quotes, as data (`previousQuotes`).

A correction never says what the verdict should be, and the same refusal always gives the same correction.

**No identical resend.**
- A problem is keyed by its code plus the quote side, for example `quote_not_found:source`.
- If a problem comes back after its correction, that relationship stops. `stoppedBecause` is `repeated_contract_error`, `repeated_evidence_error`, `repeated_coverage_error` or `repeated_output_error`.
- A new problem may be corrected once more, within 3 attempts per relationship (`attempt_limit`).
- For one relationship, being left out of a list and getting an empty list count as the same problem.

**Debugging details are kept.**
- Each refusal records `problems`: the code, the side, and `from` for a quote copied from another relationship.
- It also records `given`: the refused quotes, clipped to 300 characters.
- An unverified judgement carries `failureCodes`, `attempts`, `stoppedBecause` and `refusals`.

**Other rules.**
- A relationship that quoted another relationship is asked alone at once.
- Judgements that already verified are kept and never asked again.
- With every stage off the cascade is unchanged and no correction is sent: `RETRY.corrections` is dropped from the prompt.

## 4. Empty and partial answers (`validate()`)

- An empty `judgements` list, when relationships were asked, is refused for every one of them as `empty_answer`. The message is unchanged: "AI omitted alignment judgements".
- A relationship left out of a non-empty list is refused as `not_answered`. An unknown or duplicate id is refused too.
- Nothing is made up. A relationship without a valid judgement is reported as INSUFFICIENT_EVIDENCE with its reasons, and the check is incomplete.
- A partial answer keeps its valid judgements. Only the missing or refused relationships are asked again, with corrections, inside the request and cost guards.

## 7. Flagged for faculty review: `vu-prog1-name-only`

The proposed expectation is unchanged: PARTIALLY_ALIGNED or NOT_ALIGNED, with `valueUse: name_only`. The item is flagged in `docs/academic-validation-package/`: its record shows the live answer and the question, and the README lists it under "Flagged for faculty review".

**The lesson text.**
- Activity: "Pair programming in the laboratory: students write if-else programs and review each other's code".
- Task: "write and test an if-else program".
- Value statement: only the name "Humility". No institutional definition is supplied.

**The model (E.4, live):** ALIGNED, with `valueUse integrated`, `carriedBy activity` and `valueFit fits`. Its explanation: "Students review each other's code during pair programming, which can express Humility through acknowledging mistakes and accepting constructive feedback."

**Does the instructional evidence demonstrate the value?** In the assistant's reading, not by itself. The text shows an activity that could carry Humility, not students living it:
- The behaviours that would show Humility are not in the text: acknowledging one's own errors, revising one's code from a partner's feedback, or crediting a partner's contribution. The model supplied them with "can express".
- Reviewing each other's code is just as consistent with quality checking or collaboration, which is closer to Community-orientedness. The text does not say which.
- When no definition is supplied, the D1 test itself requires judging "only whether the lesson text itself shows students acting in a way that expresses the named value".

**The prompt led the answer.**
- The D1 test's own example reads: "Humility is integrated by a peer code review in which students acknowledge their own mistakes and accept constructive feedback".
- The model repeated that example nearly word for word, without its decisive condition ("in which students acknowledge …").
- The example also overlaps a dev-split evaluation item, so agreement on this item is not independent evidence.

**For faculty to decide:**
- whether this lesson shows Humility being lived, or only an opportunity for it;
- whether a value counts as integrated when an activity could carry it but the syllabus does not say how;
- what wording would demonstrate Humility under the institution's definition. The LCUP wording is still pending approval.

**Possible follow-up** (needs approval; not done): replace the D1 example with one outside the evaluation set, or state its evidence condition explicitly. That would be a new revision (r7), after which this item should be measured again.

## 9. Remaining limitations

- **No faculty review yet.** The expected labels are provisional (developer-written, unreviewed), and no item has a faculty review. No agreement figure here is faculty-verified.
- **The live sample is small:** 8 relationships of one course, and one Ref-relevance answer. The swap fix rests on that one live answer and on the offline tests; `rr-prog1-relevant` has not been asked again.
- **Empty answers** are a model behaviour: 2 of the 5 first answers. The corrections recovered one, but each cost a request.
- **Strict quotes** refuse a near-verbatim quote, such as one with a capitalised first word. This is deliberate: the evidence requirement is not weakened. The correction for it is untested live.
- **Structured fields:** a `not_assessed` value in a type's own field is accepted as "not known", by design, because nothing is guessed.
  - In this run `af-syseng-irrelevant` left `teaching` and `learnerSupport` unassessed, and `vu-syseng-community` left `carriedBy` unassessed.
  - Their labels, quotes and recommendations still verified.
- **Drafts** are checked by heuristics only (copies and kept off-subject wording). Their academic correctness is not verified.
- **Pending approvals and reviews:**
  - the value definitions (the LCUP wording) await institutional approval;
  - the APA rules await a librarian's check;
  - the Tagalog wording added since E.1 awaits a native speaker.
- **Caps are not bills.** The guard's accounting is deliberately conservative: the highest list price, with no cache.
