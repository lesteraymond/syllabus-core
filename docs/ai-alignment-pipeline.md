# AI alignment: the pipeline, and where a wrong judgment can come from

Traced from the code (not from the generated rules file) on 2026-10-23. "Observed" means it was seen in a model's actual output; "possible" means the code allows it but no case has been seen.

Alignment covers ILO → CLO, CLO → EGA, CLO → PO, and the whole-list questions CLO → any PO / any EGA (advisory). Everything below runs in `server/lib/syllabuscheck/` unless another path is given.

| # | Stage | What happens (file) | How it can produce a wrong judgment | Status |
|---|---|---|---|---|
| 1 | **Input extraction** | `subjectOf()` in `routes/compliance.js`: the author's check reads their saved draft; an administrator's reads the latest submitted version with the catalog snapshot it was submitted with. An uploaded file is rule-checked only, never AI-judged. | A check judges the **saved** form, not unsaved edits (the builder saves first). A stale snapshot is judged as submitted. | By design. No defect seen. |
| 2 | **Normalization** | Almost none. Outcome texts are sent as written. Whitespace is normalized only when matching a quote (`evidenceQuote`). No truncation of CLO, ILO or PO text. Truncation exists elsewhere: course description 1,500 chars, plan topics 3,500 chars, at most 12 course outcomes in the context block. | Acronyms, case and spelling are the model's to interpret. Truncation affects only the description check and the context block. | Possible only for very long descriptions. |
| 3 | **Curriculum and program context** | `repository.mastersFor()`: school vision, mission and **EGAs** from `institution_egas`; the program found from `content.meta.program` (code or alias) with **its own POs** from `program_outcomes`; approved curricula. An unknown program gives no POs (`PO-MASTER`, blocking). | **EGAs are names only** (e.g. "Competent Catholic Augustinian-Marian Professional"): no official description exists in the data, so every CLO → EGA judgment is made from a few words. The code also supports per-program EGAs (`program_egas`), but the checker always sends the school-wide list; today the two lists are identical for every program, so no error results. | **Limit on accuracy** (EGA definitions missing) and a **latent mismatch** (per-program EGAs). Both are policy/data questions, not changed. |
| 4 | **PO and EGA resolution** | `pairsOf()` looks up the tagged number in `masters.pos` / `masters.institution.egas`. Duplicate, missing or nonexistent tags are blocked by `CLO-MAP` and `ILO-MAP` (`validation.js`). | A tag to a PO that does not exist gives an **empty** source; it is reported by the fixed rule and not sent to the AI. The AI cannot substitute another program's PO because it is never given one. | Verified by `institutional.test.js` and `alignment-safety.test.js`. |
| 5 | **Relationship construction** | `pairsOf()`: one pair per tag (CLO-PO, CLO-EGA, ILO-CLO), plus the whole-list pairs. Source and target are the plain texts. | The PO is sent as its text only (not its number or short name). The CLO is sent as its statement only, not its title or level. | No error seen. |
| 6 | **Prompt creation** | `PROMPT` in `gemini.js` (version `alignment-10`) plus the `course` block (code, title, program, year, description, CLO statements). Variants for testing are in `variants.js`. | Observed and fixed earlier: the prompt did not say which side is source and which target (ILO-CLO answered "no ILO supplied"). **Possible, not yet measured:** the line "when in doubt choose PARTIALLY_ALIGNED"; the rule that every part of a multi-part PO must be shown (a specific CLO rarely covers a whole PO); the Bloom-level test. | Direction fixed. Doubt rule and PO-coverage wording are tested as variants (`calibrated`, `rubric`) but **not yet measured** (no provider credit). |
| 7 | **Model call and retries** | `requestOpenRouter` / `requestGemini` in batches of 8 (free model) or 12; `judgeBatch()` re-asks only the failed relationships; HTTP, quota and timeout errors are not retried (a timeout splits the batch once). | **Observed:** the same pair judged differently alone and in a batch; the model sometimes copies the target text as its source quote; the provider can throttle (429) or run out of credit (402). | Provider failures are classified (`failure.kind`) and never become a verdict (`alignment-safety.test.js`). |
| 8 | **Parsing and validation** | `verifyAnswer()` → `validate()`: valid JSON, every requested id once, no extra fields, a verdict from the four values, a non-empty explanation, quotes found in the matching text, supported Bloom levels, a draft for PARTIAL/NOT_ALIGNED. `rejections()` says why an answer was refused. | **Observed:** a **label that contradicts its own explanation** ("cannot support the course" with ALIGNED). Validation cannot see that. Also possible: a fluent but wrong explanation with real quotes. | The prompt now requires the label to agree with the explanation (REF-plan). Not provably fixed. |
| 9 | **Verdict normalization** | None beyond the enum: `aligned` or `MOSTLY_ALIGNED` is refused, not mapped. | A mis-cased or invented verdict makes the answer unverified, never a guess. | Tested (`output-validation.test.js`). |
| 10 | **Caching** | `pairKey()` = prompt version + variant + provider + model + type + both texts + course context; verified verdicts of the last 3 runs of the same syllabus are reused. | A **wrong verdict is frozen** until a text it depends on changes. The CLO list in the context block is deliberately not in the key (an edit to one CLO would re-ask everything). A stored verdict is never reused across models, prompts or variants, and a synthetic "empty text" judgement is never reused. | Tested (`cache-keys.test.js`, `variants.test.js`). |
| 11 | **Scoring and recommendations** | `engine.js`: −3 NOT_ALIGNED, −1 PARTIALLY_ALIGNED per scored relationship; a CLO needs one aligned PO and one EGA, an ILO one aligned CLO; one suggestion per field. Advisory relationships cost nothing. | A **false rejection** costs points and produces a rewrite that may change the meaning; a **false approval** hides a gap. | Official scoring unchanged. |
| 12 | **UI** | `src/lib/hybridView.js` and `HybridCheckPanel`: each non-aligned relationship is a problem with its explanation and quotes; scored ones are "fix first", advisory ones "improve". | **Found and fixed in this pass:** the panel treated only reference pages as advisory, so ILO-content, Description-plan and CLO whole-list verdicts were shown as "fix first / high" although the server gives them no points. | Fixed; tested (`hybridView.test.js`). |

## Where each error in the baseline came from

| Error | Source |
|---|---|
| Cooking book judged ALIGNED | Model reasoning (label contradicts explanation) |
| REF-plan answers refused | Prompt design (source/target direction) → output validation correctly refused them |
| ILO-CLO answered INSUFFICIENT_EVIDENCE | Prompt design (direction), and a duplicate of the CLO in the context block |
| Interdisciplinary CLO judged PARTIAL | Ambiguous label |
| Programming ILO-CLO judged PARTIAL in a batch | Model limitation (batch context) |
| 4 of 9 REF-plan answers still invalid with prompt 10 | **Not diagnosed** (the reasons were not recorded then; they are now) |

No evaluation-harness defect, cache contamination or retry/fallback defect was found. One harness limitation: before this pass it called the provider once without the app's retry path, so it overstated the invalid-answer rate; it now uses `judgeBatch()` and reports both.
