## 1. Root causes (Stage E.3 Phase 1 smoke, run 2)

Evidence is in `docs/ai-eval-stage-e3-smoke-run2.json`. The run used `minimax/minimax-m3.1-flash` on OpenRouter with every stage on (`alignment-12ab34c1c2d1d2-r4`), under caps of 10 requests and $0.05.

**What happened:**
- 16 relationships were planned, 8 for each of two courses. All 8 model requests went to the first course's batch of 8, and the run stopped at the request cap before reaching the second course.
- 1 of the 8 responses verified as a whole. Only 2 of the 8 relationships asked ever verified.
- 4 relationships were never asked a second time.
- Usage: 52,253 prompt tokens, of which 38,528 were cached, and 4,581 completion tokens. The provider reported $0.0054; at the highest list prices the run cost $0.0212.

**The five causes:**

1. **One message for unrelated problems.**
   - The first response was refused as "Invalid or duplicate AI judgement" for 7 of its 8 relationships.
   - That one message covered a malformed field, an unknown or duplicate id, an invalid label and an empty explanation, so the log could not say which one occurred.
   - The actual problem was 7 empty explanations.
   - Quote refusals had the same flaw. Each said only "AI evidence is not present in the supplied text". In fact 3 of the 13 later answers had swapped quotes or quotes taken from another relationship.
2. **A re-tag had no valid answer.**
   - For a sound CLO (or ILO) with a wrong tag, the r4 prompt told the model to return the unchanged text as the draft. The model returned an empty draft instead.
   - Every misalignment required a non-empty draft, so the answer was refused with "A misalignment must include a usable draft revision", every time:
     - `cp-bsit-wrongpo`, a sound CLO with a wrong PO tag, was refused 4 times this way;
     - `ic-prog1-wrongclo` was refused once.
   - At temperature 0, the same question gets the same answer.
3. **The retry cascade spent the budget on repeats.**
   - The cascade kept what verified, asked the rest again, halved, then gave each single relationship 3 tries.
   - `cc-prog1-offsubject` was sent 7 times. `cp-bsit-wrongpo` was sent 5 times; its 6th send was refused by the cap.
   - Four relationships (Activity-fit, Assessment-fit, Value-use, Ref-relevance) got no second request.
4. **Batches too large for the staged answer.**
   - With every stage on, an answer carries up to 22 fields per relationship.
   - In the batch of 8, 7 explanations came back empty. None were empty in the 13 answers given in batches of 1–4.
5. **Guard gaps in the other paid scripts.** Found while reviewing, not seen in run 2. Per `docs/live-evaluation-plan.md`:
   - `eval-alignment.cjs` capped requests, but the operator was expected to check its cost by hand after each dataset;
   - `live-pipeline-eval.cjs` checked its cost cap between syllabi.

## 2. Response contract (re-tag vs. rewrite)

While Stage A or Stage B3 is on, every answer has a `recommendation` field. The JSON schema sent to the model asks for it. With both stages off, the field does not exist and the prompt is unchanged.

| Recommendation | When | Draft |
|---|---|---|
| `NO_CHANGE` | The label is ALIGNED. | None. |
| `REWRITE_TEXT` | A misalignment whose text must change. | The complete revised text. **Required**: an empty, blank, null or left-out draft is refused (`missing_draft`). |
| `RETAG_OUTCOME` | A misalignment whose text is sound but whose tag is wrong. Allowed only for CLO-PO and CLO-EGA (Stage A) and ILO-CLO (Stage B3). | Empty. The text stays exactly as written. A draft that is left out, null, or only repeats the current text is treated as empty; a changed text is refused (`retag_with_rewrite`). |
| `REVIEW_REQUIRED` | INSUFFICIENT_EVIDENCE, or an advice-only relationship that is not aligned. | Empty or one sentence. Refused for a misalignment that has a field to rewrite (`recommendation_not_allowed`). |

**What a re-tag answer leads to:**
- No rewrite is offered.
- The finding names the tag as the field responsible (`responsible: po_mapping` or `clo_mapping`).
- **Re-tag advice is given only when the whole-list check verified another approved outcome.** The outcome must be in the approved list, not already tagged, and its own text must hold the quoted evidence.
- Otherwise no outcome is invented. The tag field is listed for the author's decision (`retag_needs_review`, status NEEDS_REVIEW, recommendation type REVIEW_REQUIRED).

**Safeguards:**
- No tag and no text is ever changed automatically, and a wrong tag is never reported as aligned. Its finding and points stay.
- An answer that leaves out the recommendation field is held to the earlier rule (a misalignment needs a draft), so leaving it out never lets more through.
- A draft field that is left out or null is read as empty only when the answer recommends RETAG_OUTCOME or REWRITE_TEXT. A re-tag then stays valid without any rewritten text, and a rewrite is refused as `missing_draft`. In any other answer a missing draft is still a `schema` error.
- The prompt wording is in `stages.js`: `R.contract`, and the re-tag sentences in `A.cloPoTail` and `B3.iloTail`.

## 3. Validation errors (one code per problem)

**How refusals are reported:**
- `checkOne()` in `gemini.js` gives each problem its own code and message.
- An answer with several problems lists all of them (`codes`, `problems`); the messages are joined with "; ".
- Every refused relationship keeps its own reason in `rejected`. The generic "invalid or duplicate" message is gone.

**The codes:**
- **Structure:** `schema`, `unknown_id`, `duplicate_id`, `not_answered`, `invalid_label`, `empty_explanation`.
- **Quotes:** `quote_missing`, `quote_not_found`, `quote_wrong_side`, `quotes_swapped`, `quote_from_other_pair`.
  - `quote_from_other_pair` names the relationship the quote came from.
- **Drafts and Bloom levels:** `invalid_bloom`, `missing_draft`, `draft_too_long`.
- **Recommendations:** `invalid_recommendation`, `recommendation_conflicts_label`, `recommendation_not_allowed`, `retag_not_applicable`, `retag_with_rewrite`.
- **Role confusion** (`role_confusion`, any stage on): the explanation describes the CLO with the ILO's words and the ILO with the CLO's. Hedged or contrasting clauses are never counted.
- **Unreadable replies:** `invalid_json`, `invalid_answer`, `incomplete_output`.

The full table, with which codes count as contract errors, is `docs/ai-checker-rules.md` section 9c.

**Quote checks stay strict:**
- A quote must be in its own side of its own relationship.
- A quote that appears only elsewhere in the batch is refused, never accepted.
- A relationship whose explanation or evidence is missing is never counted as verified.

**What every decision keeps.** Each AI finding in the verdict carries:
- the relationship (`relationshipId`);
- its status, evidence and explanation;
- the recommendation type (`recommendationType`);
- where one field is to blame, that field (`responsible`).

## 4. Retry policy and batch size

**With any stage on**, `judgeBatch` uses `judgeStaged`:
- **Batch size:** 4 relationships per call (`STAGED_BATCH`).
- **Partial answers:** the judgements that verified are kept, and only the failed relationships are asked again.
- **Attempt cap:** each relationship is sent at most 3 times (`MAX_ATTEMPTS`): in its batch, once more with the others that failed with it, then alone.
- **Contract errors are not retried a third time.** A relationship refused twice in a row for the same contract code stops there (`stoppedBecause: repeated_contract_error`). These are deterministic mismatches between the answer and the contract.
  - Other failures stop after the third attempt (`attempt_limit`).
- **Unreadable replies.** A reply that names no relationship (broken JSON, a cut-off reply) is not blamed on any one relationship. Its relationships are asked again in two halves, and the reply still counts as an attempt for each of them. A relationship with one attempt left is always asked alone.
- **What a failure reports.** A relationship that never verified is reported as INSUFFICIENT_EVIDENCE with:
  - every refusal code (`failureCodes`);
  - its `attempts` and `stoppedBecause`.

  The check is then incomplete, so no official score is shown.

**With every stage off**, the legacy cascade and batches of 12 (8 for free models) are unchanged. No compatibility test justified changing them.

## 6. Recommendation quality (`engine.js`, `verdict.js`)

- **A CLO not about the course comes first.**
  - When Course-CLO is NOT_ALIGNED, the CLO's drafts toward its POs and EGAs (and toward the whole lists) are not offered. They are withheld as `clo_off_course`, so a rewrite never fits the CLO to a subject the course does not teach.
  - The rewrite for the course is offered first. The findings and points are unchanged.
- **A re-tag and a rewrite are never both offered.**
  - When every failing tag of a CLO's group says "keep the text", a CLO rewrite built only from those tags is withheld (`retag_conflict`).
  - The contradiction checker (`eval/contradictions.js`) flags any re-tag advice that sits next to a rewrite of the same field.
- **Drafts get a static review** (staged checks, no model call).
  - A draft that copies the text it is checked against (`copies_reference`) is not offered.
  - So is a draft that keeps most of the off-subject topic words of the text it replaces (`keeps_off_subject`). Action verbs are exempt, because they state the competence the rewrite must keep.
  - The field is listed for the author's decision (`draft_needs_review`).
- **Role confusion** (an explanation that swaps the CLO's and the ILO's roles) is refused at validation (section 3).
- **What remains unverified:** whether a draft is academically right needs another judgement. It is never claimed; such a draft is either offered as a suggestion for the author, or listed as REVIEW_REQUIRED.
- Nothing is applied automatically.

## 7. Provider guards (`server/lib/syllabuscheck/eval/providerGuard.js`)

All three paid scripts now send every HTTP request through one guard, which checks it **before** it is sent: `live-smoke-eval.cjs`, `eval-alignment.cjs` and `live-pipeline-eval.cjs`. The comparison script `eval-compare.cjs` needs `--confirm-paid` and passes the guard's limits to `eval-alignment.cjs`.

**Before each request:**
- **Request cap.** It counts retries and price lookups. A ledger file carries the count into the next invocation.
- **Cost cap.** It is checked against each request's worst case: every request byte as an input token, plus `max_tokens`, at the highest price any endpoint lists. Requests still in flight hold their reservation. With no current prices or no `max_tokens`, nothing is sent.

**Stop conditions:**
- HTTP 401, 402 or 403, or any other refusal of the request format, stops the run at once. After that every request is refused locally, so nothing is sent after a provider-credit failure.
- The configured invalid-answer and timeout limits stop it too.
- An answer cut off while it is read counts as a timeout. OpenRouter sends the HTTP 200 headers at once and holds the connection while the model works, so a request's timeout can fire after the headers have come. Such a request is charged its worst case, counted toward the timeout limit, and thrown as a timeout. This was added after the Phase 1 re-run (section 13).

**Run safety:**
- Completed results are written when a run stops.
- The API key is redacted from every error, log, ledger and result, and request headers are never kept.
- The global `fetch` is blocked, so nothing goes around the guard.
- The stage switches live in a local env object (`process.env` and `server/.env` are untouched), and no database, route, repository or service module may be loaded.
- `live-pipeline-eval.cjs` checks its budget per request, not only between syllabi.

**Flags:**
- `eval-alignment.cjs` now needs `--confirm-paid` for a paid run, and `--plan` shows the cost without a call.
- `live-pipeline-eval.cjs` and `live-smoke-eval.cjs` need `--live --confirm-paid`.

## 10. Remaining limitations

- **Semantic checks:** whether a draft is academically correct is not verified. The static draft review is a heuristic (word stems) and catches only copies and kept off-subject topics. Role-confusion detection catches only full role swaps with no hedging.
- **Re-tag advice** depends on the whole-list check naming an approved outcome whose own text holds the quote. When it does not, the tag waits for the author.
- **SEM-TAG wording** says "another tag is aligned" even when only the whole-list answer is aligned.
- **`responsible` is null** for CLO-anyPO, CLO-anyEGA, ILO-content, Description-plan, Plan-sequence and REF-plan findings.
- **Legacy path:** with every stage off, unreadable replies can still send a relationship 4 times. This is unchanged by design.
- **Request volume:** a fully valid staged check sends about 2.5 times the requests it did before (48 against 19), as section 5 shows.
- **Tagalog:** the new strings need review by a native speaker.
- **Live behavior, little evidence so far:** the contract has been checked live on 7 relationships of one course (section 14). The second course was not verified. Ref-relevance cannot verify until its prompt wording is fixed, and one answer came back empty.
- **Evaluation datasets:** these are developer-written and unreviewed by faculty. A match is not faculty-verified accuracy.

**Findings:**
